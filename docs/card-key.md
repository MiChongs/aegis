# 卡密系统

> 面包屑：[Aegis](../CLAUDE.md) › 卡密

应用级的卡密（激活码 / 兑换码）。一张卡有两种形态，共用同一套生成、作废、
核销与权益目录，只有「怎么被使用」不同：

| 形态 | `kind` | 怎么用 | 终态 |
|---|---|---|---|
| 授权卡 | `login` | 卡**就是**登录凭证。首次使用自动建号并绑定，之后凭卡登录 | `active`（授权期内可反复登录） |
| 兑换卡 | `redeem` | 给已登录用户发权益 | `used`（一次性） |

两种形态共用一张 `card_keys` 表而不是各建一张：生成、导出、作废、查询、
核销记录这五件事逐字相同，分表意味着这五处逻辑各写两遍，而它们迟早会漂移成两套行为。

## 授权卡：卡即账号

```
POST /api/v1/apps/{appKey}/auth/login
{ "method": "cardkey", "cardKey": "VIP-A3K9-M2P7-QXR4-T8WN", "deviceId": "…" }
```

**不新增路由** —— `/auth/login` 是单一登录入口，`method` 就是分发点。
加一种登录方式不加路由，客户端也就不需要认识第二条登录入口。

响应在标准会话字段之外多一个 `authorization`（授权到期时间、可绑设备数、
已绑设备数）。这三项随登录一起下发而不是让客户端再问一次：它们正是买了卡的用户
最想确认的东西，分两次请求就意味着「登录成功但授权信息拿不到」是一种可能的状态。

### 账号名由卡面派生

`users.account` 就是卡面本身。这不是偷懒，它让「首次使用自动建号」变成一次
**确定性**操作：用随机账号名的话，同一张卡的两次并发首登会造出两个账号，
其中一个成为谁也够不着的孤儿；用卡面则第二次会撞上 `uq_users_appid_account`，
服务层据此回读同一个用户即可。

账号没有密码（`password_hash` 为 NULL），与短信建出来的账号同一形状 ——
`verifyCredential` 对空哈希会跑一次哑 bcrypt 再返回 false，因此这类账号
天然无法用密码登录，不需要额外挡。想改用密码登录走「设置密码」流程。

### 续期

同一个用户可以绑多张授权卡，因此 `bound_user_id` 上**没有**唯一约束。
续期的动作是「登录状态下核销一张新的授权卡」，它会绑到当前账号并各自计时。
两张卡都在授权期内时，任意一张都能登进同一个账号。

### 设备绑定

`card_key_devices` 是「一卡三机」的载体。现有的任何一处都放不下这个语义：
登录一致性基线是「一个用户绑一台设备」且只活在 Redis 里（会过期），
`device_fingerprints.device_id` 是全局唯一的（一行一设备，不是多对多）。

绑定的写法是**先 UPSERT 再数总数**，不是「先数再插」：后者在同一张卡的两台设备
并发首登时会双双读到 `count = max-1`，各自插入，结果绑上 `max+1` 台。

**缺设备标识时拒绝而不是放行**（40343）。开着的限制因为请求没带标识就放行，
等于没有这个限制 —— 与试用的设备去重同一取向。

解绑（控制台上单卡的「设备」抽屉）是「用户换电脑了」唯一的出口：
设备标识会随重装系统变化，没有它，一张一机卡在用户重装之后就永久报废了。

## 兑换卡：一个事务，七档权益

```
POST /api/v1/apps/{appKey}/card-keys/redeem
{ "code": "…", "deviceId": "…" }
```

七档权益由 [`internal/domain/cardkey/catalog.go`](../internal/domain/cardkey/catalog.go)
这份**目录**定义，它同时驱动服务端校验、控制台的权益编辑表单与展示文案：

| 权益 | 落到哪 |
|---|---|
| `vip_plan` | `extendUserVipTx`，继承套餐的时长与功能标识快照 |
| `vip_days` | `extendUserVipTx`，不挂套餐、不带功能标识 |
| `integral` | `applyIntegralChangeTx` |
| `experience` | `applyExperienceChangeTx`（本次新抽出的事务内助手） |
| `balance` | `applyWalletChangeTx`，类型 `card_key` |
| `lottery_draws` | `lottery_draw_grants`（本次新建的余额表） |
| `device_slots` | 改写该用户授权期最长的那张授权卡的 `max_devices` |

新增一档权益只需目录加一行 + `grantCardRewardsTx` 加一个 `case`，控制台零改动即自动出现。
`TestRewardCatalogHasGrantBranch` 双向钉死「目录 ↔ 发放分支」：
目录多一条 → 配得上却发不出来；发放多一条 → 控制台配不出来。

### 一码一用有三道保证

叠在一起，各自防的是不同的失效模式：

1. **行锁**（`SELECT … FOR UPDATE`）—— 同一张卡的并发请求串行化
2. **条件 UPDATE 抢占**（`WHERE status = 'unused'`）—— 状态机的唯一跃迁，
   与 `FulfillPaymentOrder` 同构
3. **`uq_card_key_redemptions_card` 唯一约束** —— 兜住前两道被改坏的情况，
   而那种 bug 的表现是重复发钱

任何一步发放失败整体回滚，核销权随之释放，下一次兑换会自动重试。

### 抽奖次数是新建的概念

抽奖此前没有「次数」这个东西：`dailyLimit` / `totalLimit` 是数 `lottery_draws`
的历史行数出来的，没有任何地方存得下「这个人还剩几次」。

赠送次数**跳过日限、总限与积分扣费**：那三项限制是给常规抽奖入口用的，
让它们把买来的次数吃掉等于卡密白买，而用户无从得知次数去了哪里。
消耗走条件 UPDATE（`WHERE balance > 0`），失败路径会把次数还回去。

> 顺带修掉一处既有问题：`LotteryService.Draw` 原本先扣积分再查奖池，
> 于是「活动没有配置奖品」这个配置错误要由用户先付出代价才暴露。
> 现在奖池检查排在扣费之前。整条 `Draw` 仍然不是事务的（库存、抽奖记录、
> 自动发奖是三次独立往返），那是独立的一件事。

## 有效期的三种模式

| 模式 | `expires_at` 何时写入 | 适用 |
|---|---|---|
| `permanent` | 不写 | 永久授权 |
| `fixed_until` | **生成时**写死 | 「活动期间有效」 |
| `days_from_first_use` | **首次使用时**写入 | 卡密的常态 |

第三种是常态的原因：卖出去到被使用之间的时间不该算进用户的授权期。

**「已过期」不是一档状态**。它是 `expires_at` 与当前时间比出来的结论 ——
存成状态就需要一个定时任务去翻它，而那个任务停掉的表现是「过期卡还能用」。
列表筛选里的「已过期」在 SQL 里被翻译成时间条件，控制台上的徽标也是算出来的。

## 卡面

`PREFIX-XXXX-XXXX-XXXX-XXXX`，随机段的字符集是 32 个字符，**剔除了 I / O / 0 / 1**：
卡密是要被人抄写的（贴在卡片上、发在群里、手打进客户端），而这四个字符
在绝大多数字体下两两难辨。32 正好整除 256，因此可以直接对随机字节取模而不引入偏置。

**前缀不受这条约束**，A–Z 与 0–9 全都可用：防混淆是为了让人抄得对随机字符，
而前缀是运营自己起的可读标签（`VIP` / `GIFT` / `2026`），有上下文消歧。
照随机段的字符集校验会把 `VIP` 判成非法（`I` 不在集合里）。

同理，`NormalizeCardKeyCode` 保留的是 A–Z0–9 全集并把 `_` / 空格归一成 `-`。
按防混淆字符集过滤会把 `VIP-…` 悄悄削成 `VP-…`，表现是「明明抄对了却提示卡密不存在」。

生成时两层去重：批内用集合（1 段 3 位只有 32768 种组合，生日碰撞是真实的），
批外查库（同一应用里可能已经存在同样格式的老批次）。
格式空间装不下请求数量时**提前报错**，而不是让撞码以「生成到一半失败」的形式出现。

## 错误码

`400xx` 段在本项目里已经用满，卡密自身的判定落在 403 / 404 / 409 的空段。
面向接入方的码随 `/config` 下发（`gatewayErrors`），SDK 据此映射成分类异常。

| 码 | 名 | 含义 |
|---|---|---|
| 40340 | `CARD_KEY_DISABLED` | 已被作废（卡或整批） |
| 40341 | `CARD_KEY_USED` | 已被使用 |
| 40342 | `CARD_KEY_EXPIRED` | 已过期 |
| 40343 | `CARD_KEY_DEVICE_LIMIT` | 设备数已满，或请求没带设备标识 |
| 40344 | `CARD_KEY_BOUND_OTHER` | 已绑定其它账号 |
| 40345 | `CARD_KEY_KIND_MISMATCH` | 授权卡与兑换卡用错了入口 |
| 40346 | `CARD_KEY_NO_LOGIN_CARD` | 要加设备位但名下没有授权卡 |
| 40441 | `CARD_KEY_NOT_FOUND` | 卡密不存在 |
| 40910 | `CARD_KEY_REDEEMING` | 正在被核销（并发） |

判据分得细是有原因的：「已作废」「已用过」「已过期」对用户是三件完全不同的事，
合成一句「卡密无效」的结果是客服无从判断该补发、该解释、还是该退款。
`checkCardUsable` 的判定顺序即错误优先级 —— 一张被作废的过期卡报「已作废」而不是「已过期」。

## 控制台

`/apps/{appKey}?tab=card-key`，三个视图：批次 / 卡密 / 核销记录。

- **导出按 batchId，不按当前筛选**：生成完立刻导出时列表可能还没刷新到那一批，
  按筛选导出会得到一份不完整的卡，而那份文件是要发给渠道的。
- **批量作废按选中的 id 列表**，不做「按筛选条件批量」：管理员看到的列表与实际执行
  之间存在时间差（翻页期间有人兑换），按条件批量会误伤没被看过的卡。
- **已核销的卡不参与作废**：那笔权益已经发出去了，改它的状态只会让核销记录与卡状态自相矛盾。
- **停用批次不改单卡状态**：卡还是那些卡，只是这一批整体不再可用。逐张改成 disabled
  会让「先停批次、再启用」变成不可逆操作 —— 那些本来就已经被作废的卡分不出来了。
- **核销记录展示 `results`（实际发放）而不是 `rewards`（卡上配的）**：
  两者绝大多数时候一致，但排障要的恰恰是不一致的那些情况。

**「卡密登录」的开关不在卡密区块**，而在「接入」（`?tab=auth-protocol`）的登录方式里。
在卡密区块再放一个就是同一件事的第二个配置入口，接入方无从判断哪个生效。

## 客户端

官方 Kotlin SDK：

```kotlin
// 授权卡登录（deviceId 必填）
val session = aegis.auth.loginWithCardKey(cardKey = "VIP-…", deviceId = deviceId)

// 兑换卡
aegis.commerce.redeemCardKey(code = "GIFT-…")

// 我的授权
aegis.commerce.myCardKeys()
```
