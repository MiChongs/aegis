# 支付凭证（多语言 PDF）

> 面包屑：[Aegis](../CLAUDE.md) › docs/payment-receipt

用户和管理员都能为一笔支付订单导出一份 A4 凭证 PDF：
收款方、付款方、商品明细、税费与折扣、支付信息、退款记录、附注一应俱全，
**默认英文**，共 10 种语言，中日韩由外部字体承载。

## 版式与配色

整份凭证的视觉语言是 **暖象牙纸面 + 暖近黑文字 + 单一珊瑚强调色**，
与 Claude / Anthropic 的调子一致：**全页只有一个彩色**，其余层级全部由暖中性灰承担。
这比多色方案更耐看，也更像一份正式凭证而不是一张宣传单。

| 角色 | 值 | 用在哪 |
|---|---|---|
| 珊瑚强调 | `#D97757` | 页首色带下沿、附注卡片的竖条 |
| 强调文字 | 珊瑚的深色调 | 合计金额 |
| 品牌标记底 | 珊瑚再深一档 | 圆角方块 + 品牌首字母 |
| 象牙 | `#F0EEE6` | 页首色带、表头行、汇总面板 |
| 纸色 | `#FAF9F5` | 附注卡片 |
| 主文字 | `#141413` | 正文（暖近黑，纯黑在暖底上显脏） |
| 中性灰 | `#3D3D3A` / `#6B6B66` / `#76766F` | 次级正文 / 说明 / 标签 |
| 状态色 | 绿 `#3F7A55`、琥珀 `#B0742A`、砖红 `#B4432F` | 徽标；**文字另用深一档** |

版式上的几处具体决定：

- **页首是一整条色带而不是一条分隔线**。线只是把两部分分开，色带能立住抬头。
- **合计做成带描边的圆角面板**。它是整份凭证上唯一被反复查看的数字，需要一个明确的边界。
- **小标签全大写并拉开字距**。8pt 的全大写不拉字距会挤成一团黑块。
- **同一表格行里的数字与品名同字号**。gopdf 按行盒顶部定位，字号不同的文字给同一个 y
  会落在不同基线上 —— 表格看起来就是错行的。层级差异改由颜色表达。
- **核验二维码放在汇总面板左边那片空白里**。塞进「支付信息」区会把两列键值挤到
  「Payment meth…」的程度，而对账字段被截断比没有二维码严重得多。

### 颜色不是审美，是可断言的事实

`TestPaletteMeetsContrastRequirements` **穷举渲染器真正画出来的每一组「文字色 / 底色」**，
逐组核对 WCAG 对比度：小字 4.5:1，大字 3:1。凭证会被打印成灰度、会被视力不佳的人阅读，
"看着还行"不是标准。这条测试已经挡下过三处问题：

- 珊瑚原色在象牙底上只有 2.6:1 —— 够画一条线，不够印一行字，
  所以强调文字走它的深色调（`accentText`）；
- 状态色直接当文字用同样不达标，因此另有一档 `successText / warningText / dangerText`，
  原色只用于徽标块面；
- 最初的标签灰 `#91918D` 对白底只有 3.2:1，达不到小字门槛，已加深到 `#76766F`。

表里刻意**不**做颜色的两两组合 —— 那会为了让根本不存在的组合达标而把配色改坏。
新增一处上色时要同步补一行，漏了就等于那处颜色没人守。

### 用到的库，以及为什么不换 PDF 引擎

| 库 | 承担什么 |
|---|---|
| `github.com/signintech/gopdf` | PDF 引擎 |
| `github.com/lucasb-eyer/go-colorful` | Lab 空间的色彩派生（浅调、深调）与对比度计算 |
| `github.com/boombuler/barcode` | 二维码矩阵 |

**浅色调走 Lab 而不是 sRGB 线性插值**：sRGB 里插出来的浅色会发灰发脏，珊瑚色尤其明显 ——
它的浅调在 sRGB 下会偏向粉褐，Lab 下才保持干净的暖橘。`TestTintKeepsChromaInLabSpace`
用彩度直接比对两种算法，确保这个依赖换来了实际差异而不只是多一行 import。

**二维码逐模块画成矢量小方块**，不嵌位图：凭证是要打印的，位图二维码放大后边缘发糊。
`TestVerifyURLProducesVectorQRCode` 数内容流里的矩形算子来确认它真的画出来了 ——
只断言「没报错」是不够的，画了零个模块同样不会报错。

**PDF 引擎仍是 gopdf**。评估过两个替代：

- `go-pdf/fpdf` 有内建的圆角矩形、渐变与裁剪，看起来更强 ——
  但这套设计语言是扁平的，用不到渐变；圆角矩形用多边形逼近即可
  （8 段/角，6pt 半径下最大偏差 0.03pt，远低于 300dpi 的一个像素）。
  换引擎要重写全部排版代码、重新验证中日韩子集嵌入，还会作废现有的版面校验工具链。
- `maroto` 是声明式网格布局，但它会**削弱**排版控制力（自定义徽标、字距、基线对齐都做不了），
  且其中日韩支持未经验证。

换掉引擎的收益是「少写一个圆角矩形函数」，代价是重写与重新验证。这笔账不划算。

## 两类凭证主体

平台上有**两条并行的资金记录**，两条都能出凭证：

| 主体 | 表 | 覆盖的钱 |
|---|---|---|
| 支付订单 | `payment_orders` | 走支付渠道收进来的钱 |
| 钱包流水 | `wallet_transactions` | 从余额里花掉 / 进到余额里的钱 |

第二条是必需的，因为**有三种「用钱包付的钱」根本不产生订单**：
余额直购会员（`/vip/purchase`）、业务消费（`/wallet/consume`）、管理员调账。
只认订单的话，这几笔交易的用户手里只有一行流水，拿不到任何可归档、可报销、可对账的文件。

两者共用同一套排版、同一份译文与同一条导出/寄送/清理链路，
差别只在「文档从哪装配」（`payment_receipt.go` vs `payment_receipt_wallet.go`）。

### 同一笔钱只出一份凭证

钱包流水挂着 `related_order_no` 时（充值到账、余额支付订单），
凭证**由订单出具**，钱包这边只是把同一份文档再交付一次 ——
从 `/api/wallet/transactions/{no}/receipt` 下载到的，与从
`/api/pay/orders/{orderNo}/receipt` 下载到的是同一份文件（同编号、同金额、同退款明细）。

否则同一笔交易会有两个凭证编号，对账时无从判断哪个算数。
委派前会三重校验（订单存在、同应用、同用户）：`related_order_no` 是一列没有外键约束的文本，
只按单号取回就直接用，等于把「凭证给谁」交给一个字符串决定。

## 三份不同的凭证

同一个接口按订单状态出具三种文件。这不是措辞差异 ——
**给一笔还没收到的钱开「收据」就是在伪造凭证**：

| 订单状态 | 凭证类型 | 抬头（en / zh-Hans） |
|---|---|---|
| 已支付 | `receipt` | Receipt / 收据 |
| 未支付 · 已过期 · 失败 | `invoice` | Invoice / 账单 |
| 全额退款 | `credit_note` | Credit Note / 退款凭证 |

部分退款仍是收据（钱确实收到过），但会多出退款区块与「实收净额」一行。
调用方可以用 `documentType` 显式指定，留空即按上表推导。

**钱包流水只有两档**：退款入账出 `credit_note`（这份文件此时证明的是一笔退回的钱），
其余一律 `receipt`。没有 `invoice` 档 —— 写进 `wallet_transactions` 的那一刻钱已经动了，
不存在「待支付的流水」。

凭证编号是 `RCP-<单号>` / `INV-…` / `CRN-…`，订单与钱包共用同一条规则
（单号本身就带出处：订单是 `P…`、钱包流水是 `WAL…`）。
**同一主体反复导出得到同一个编号** —— 凭证编号是给人对账用的，
每次下载都换一个号会让对账无从下手。

### 钱包凭证上写了什么

| 区块 | 内容 |
|---|---|
| 合计 | 流水金额的**绝对值**。方向由类型与附注表达 —— 印一个负数总额会让任何一款报销系统都拒收 |
| 商品栏 | 平台生成的标题走译文键（「余额支付订单」→ Order paid with balance）；`consume` 的标题是**接入方填的**消费说明，原样保留 |
| 支付明细 | 支付方式恒为「余额」，时间取流水创建时间。**没有「交易流水号」行** —— 内部账本没有上游单号，填一个会让人拿着它去找渠道对账 |
| 附加信息 | 流水号、类型、资金方向、**变动前后余额**、关联订单、经办人、套餐快照 |
| 附注 | 出账「本笔款项从该账号的钱包余额中扣除，未经过任何第三方支付渠道」；入账则相反 |

变动前后余额一定要印：一份只写「扣了 50」的凭证无法自证，
而「变动前 200 → 变动后 150」是可以与对账单逐行核对的。

## 接口

### 用户侧（`/api/pay`，需用户会话）

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/orders` · `/orders/{orderNo}` | 订单查询，每条都带 `receipt` 区块（见下） |
| `GET` | `/orders/{orderNo}/receipt` | **直接返回 PDF**，最省事的一条 |
| `POST` | `/orders/{orderNo}/receipt/email` | 寄到账号绑定的邮箱 |
| `GET`·`POST` | `/orders/{orderNo}/bill` | 生成并落盘，返回一次性下载凭据（链接可分享） |
| `GET` | `/bills/{billId}/download` | 取回上一步生成的文件 |
| `GET` | `/receipt/options` | 可选语言 + 当前环境的字体能力 |

钱包流水的三条与订单**逐条同构**（`/api/wallet`，需用户会话）：

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/transactions` · `/transactions/{transactionNo}` | 流水查询，每条都带 `receipt` 区块 |
| `GET` | `/transactions/{transactionNo}/receipt` | 直接返回 PDF |
| `GET`·`POST` | `/transactions/{transactionNo}/bill` | 生成并落盘，返回一次性下载凭据 |
| `POST` | `/transactions/{transactionNo}/receipt/email` | 寄到账号绑定的邮箱 |

下载凭据仍走 `/api/pay/bills/{billId}/download`：那条路由校验的是
(应用, 用户, 凭证标识) 三元组，与凭证主体无关，另开一条只会多一处要同步的权限判定。

### 无需登录（邮件里的链接）

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/pay/receipts/{appid}/{billId}/download?expires=&token=` | 凭签名下载，**不需要会话** |

两步式导出存在的意义只有一个：拿到一个可以发给别人的链接。
只想存一份文件的客户端走 `/receipt` 即可，不必在磁盘上多留一份含交易明细的副本。

请求参数（query 或 JSON body，全部可选）：

| 字段 | 说明 |
|---|---|
| `locale` | 期望语言，BCP 47（`zh-Hans` / `ja` / `pt-BR` …）。留空自动协商 |
| `documentType` | `receipt` / `invoice` / `credit_note`，留空按订单状态推导 |
| `timezone` | IANA 时区名（`Asia/Shanghai`）。留空按用户设置，再空则 UTC |
| `expireMinutes` | 仅两步式导出：下载凭据的有效期，上限为 `PAYMENT_RECEIPT_TTL` |

### 管理端（`/api/admin/app/payment-config`，需管理员）

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/orders/receipt` | 代开任意订单的凭证（客服 / 对账留档），**不落盘** |
| `POST` | `/orders/receipt/email` | 寄到**指定**邮箱（走审计中间件） |
| `POST` | `/receipt/options` | 同上的能力自述 |

钱包侧挂在应用命名空间下（`/api/admin/apps/{appkey}`，需管理员）：

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/wallet/receipt` | 代开任意流水的凭证，**不落盘** |
| `POST` | `/wallet/receipt/email` | 寄到指定邮箱（走审计中间件） |
| `GET` | `/wallet/transactions` | 全应用流水（用户 / 类型 / 方向 / 关键词 / 时间窗） |
| `GET` | `/wallet/stats` | 资金面板：入账 / 出账 / 净额 / 余额合计 / 分类型 |
| `GET` | `/commerce/overview` | 交易概览：订单 + 钱包 + 趋势 + 凭证能力一次取齐 |

### 统计的时间口径

`/commerce/overview` 里每种口径**按自己的时间列筛**，这是刻意的：

| 指标 | 时间列 | 为什么 |
|---|---|---|
| 已支付金额 / 笔数 / 付费用户 | `paid_at` | 钱是什么时候到的 |
| 订单总数 / 待支付 / 状态与渠道分布 | `created_at` | 待支付的单没有 `paid_at`，只能按创建时刻 |
| 已退款 | `refunded_at` | 退款成功的时刻才是钱出去的时刻 |
| 钱包出入 | `created_at` | 流水写进表的那一刻钱就已经动了，没有第二个时刻 |

全部按 `created_at` 会让「月末下单、次月初付款」的收入落在错误的月份上，
而那正是对账时最容易被质疑的一格。

趋势的**分桶粒度由服务端按跨度决定**（≤62 天按日、≤730 天按周、再长按月）
并连标签一起下发。让调用方指定粒度的结果是「拉了两年、按天分桶、七百个点」。
空桶会被补齐 —— 缺口在折线图上会被连成一条斜线，读起来像「那几天缓慢下降」，
而事实是那几天一笔都没有。

## 订单查询里的凭证入口

`/api/pay/orders` 与 `/api/pay/orders/{orderNo}` 的每条订单都多了一个 `receipt` 区块：

```json
{
  "order_no": "P12202603211030001234",
  "amount": "1288.00",
  "status": "paid",
  "receipt": {
    "available": true,
    "documentType": "receipt",
    "locale": "zh-Hans",
    "currency": "CNY",
    "downloadUrl": "/api/pay/orders/P12202603211030001234/receipt",
    "exportUrl":   "/api/pay/orders/P12202603211030001234/bill",
    "emailUrl":    "/api/pay/orders/P12202603211030001234/receipt/email",
    "emailable": true
  }
}
```

订单本体是内嵌的，JSON 上完全扁平，对既有客户端是**纯增量**。

这几项由服务端算好而不是让客户端自己拼：`documentType` 随订单状态变化
（未支付出的是账单不是收据），`emailable` 取决于用户有没有绑邮箱、邮件通道通不通，
`locale` 是按当前请求真正协商出来的结果。放到客户端就会各端各写一套，而且很快就不一致。
不能寄送时 `emailHint` 会给出可直接展示的原因（「账号尚未绑定邮箱」）。

## 语言协商

优先级从高到低：

```
请求里的 locale  →  用户设置的语言（user_settings.ui.language）
                 →  Accept-Language 请求头
                 →  PAYMENT_RECEIPT_DEFAULT_LOCALE（默认 en）
```

用户设置排在请求头**前面**：用户在应用里选过语言，那是一次明确表达，
不该被浏览器的 `Accept-Language` 覆盖掉。
每一级都按 `Accept-Language` 语法解析，因此可以直接把整个请求头塞进 `locale`。

内置 10 种语言：

| 语言 | 标签 | 需要中日韩字体 |
|---|---|:--:|
| English（默认） | `en` | |
| 简体中文 | `zh-Hans` | ✅ |
| 繁體中文 | `zh-Hant` | ✅ |
| 日本語 | `ja` | ✅ |
| 한국어 | `ko` | ✅ |
| Deutsch | `de` | |
| Español | `es` | |
| Français | `fr` | |
| Português (Brasil) | `pt-BR` | |
| Русский | `ru` | |

金额按币种的 **ISO 4217 标准小数位**格式化（日元 / 韩元没有小数位，给它们补两位是外行错误），
千位与小数分隔符、货币符号位置、日期格式都随语言变化：

| 语言 | 同一笔金额 | 同一个日期 |
|---|---|---|
| `en` | `$1,234.56` | `Mar 21, 2026` |
| `de` | `1.234,56 $` | `21.03.2026` |
| `ru` | `1 234,56 ₽` | `21.03.2026` |
| `zh-Hans` | `¥1,234.56` | `2026年3月21日` |

合计行额外附上 ISO 代码（`¥1,234.56 CNY`）—— `¥` 既是人民币也是日元，`$` 有十几个国家在用。

**新增语言不需要改 Go 代码**：往 `pkg/receipt/locales/` 放一份 `<标签>.json` 即可。
`TestLocaleCatalogsAreKeyComplete` 会以英文目录为基准，钉住每个语言的键完整性 ——
少一条译文，凭证上就会露出原始 key。

## 中日韩字体

这是整个功能唯一需要外部资源的地方，也是最容易踩坑的地方。

### 为什么拉丁不用配、中日韩必须配

拉丁 / 西里尔 / 希腊字形来自**内嵌在二进制里**的 Go 字体（`golang.org/x/image/font/gofont`），
不依赖任何外部文件。因此「一份凭证出不来」这件事在任何环境下都不会发生 ——
最差情况是降级成英文，而不是报错。

中日韩字形动辄上万个字，无法内嵌，只能来自系统或镜像里的字体文件。

### PDF 引擎只吃 TrueType 轮廓的独立字体

`gopdf` 的解析器只接受 sfnt 版本 `0x00010000` 的**独立**字体。而现实是：

| 文件 | 真实格式 | 原样喂给 gopdf |
|---|---|---|
| `msyh.ttc`、`NotoSansCJK-Regular.ttc`、`PingFang.ttc` | TrueType **Collection** | ❌ Incorrect magic number |
| `NotoSansCJKsc-Regular.otf` | CFF / OpenType 轮廓 | ❌ 同上，且无法转换 |
| `simhei.ttf` | 独立 TrueType | ✅ |

也就是说系统上的中日韩字体**几乎没有一个能直接用** ——
这正是历史上「明明装了中文字体，导出的 PDF 里中文还是没有」的根因。

`pkg/fontkit` 解决了前一类：从 TTC 中抽出指定字型、重建表目录与校验和，
产出一份独立 sfnt。后一类（`.otf`）无解，会给出一条明确的错误让运维换文件，
而不是静默跳过让人反复换不同的 `.otf` 重试。

### 配置

```bash
# 显式指定（系统里字体名字不常规时唯一的出路）
PAYMENT_RECEIPT_FONT_PATH=/opt/fonts/NotoSansCJK-Regular.ttc
PAYMENT_RECEIPT_FONT_BOLD_PATH=          # 可留空，层级会改由字号与颜色表达
PAYMENT_RECEIPT_FONT_DIRS=               # 额外搜索目录，逗号分隔
PAYMENT_RECEIPT_DISABLE_SYSTEM_FONTS=false
```

留空时的查找顺序：

```
显式路径 → PAYMENT_RECEIPT_FONT_DIRS → assets/fonts → data/fonts → 系统字体目录
```

系统字体目录按**文件名特征**过滤后才解析（noto-cjk / 思源 / 雅黑 / 黑体 / 宋体 /
PingFang / WQY / Sarasa / 霞鹜文楷 / meiryo / malgun …）。
不这样做就得逐个解析几百个字体，每个都要读全文件并建 cmap，启动会明显变慢。
装了非常规命名字体的环境用 `PAYMENT_RECEIPT_FONT_PATH` 直接指。

**Docker 镜像已预装 `font-noto-cjk`**，容器部署通常什么都不用配。

### 找不到字体时会怎样

不会报错，会**降级并如实上报**：

- 中文 / 日文 / 韩文凭证降级为英文，`localeFallback: true`，`requestedLocale` 保留降级前的语言；
- 用户数据里的中日韩字符（昵称、商品名）画不出来时替换成 `?`，
  并在 `degradedGlyphs` 里列出具体是哪些字符 —— 留一片空白无从察觉，一串问号至少看得出来。

两种情况都会打 warn 日志。启动时也会打一条字体能力摘要：

```
payment receipt renderer ready  fonts=拉丁：Go（内嵌）；中日韩：Noto Sans CJK SC（…ttc），无粗体伴侣  cjk=true
```

等到用户点「下载收据」才发现出不来中文，排查会从支付一路查到前端，
而根因只是镜像里没装字体 —— 所以这条信息在启动时就要说清楚。

`/receipt/options` 把同样的信息下发给客户端与控制台：

```json
{
  "defaultLocale": "en",
  "supportsCJK": true,
  "fontStatus": "拉丁：Go（内嵌）；中日韩：Noto Sans CJK SC（/usr/share/fonts/noto/NotoSansCJK-Regular.ttc）…",
  "locales": [
    { "tag": "en", "nativeName": "English", "default": true, "needsFont": false, "available": true },
    { "tag": "zh-Hans", "nativeName": "简体中文", "needsFont": true, "available": true }
  ]
}
```

`available: false` 的语言选了也会被降级，客户端应当直接置灰。

## 邮件寄送

一封凭证邮件由三部分构成，缺一不可：

| 组成 | 说明 |
|---|---|
| **PDF 附件** | 渠道支持附件时直接附上（SMTP 支持，Zeabur 不支持，见下） |
| **签名下载链接** | **恒附带**，即使已经带了附件 —— 邮件会被转发、附件会被网关剥离、手机客户端未必肯下载附件 |
| **与 PDF 同语言的正文** | 邮件文案与 PDF 共用同一份译文与**同一次**语言协商结果 |

最后一条是刻意的：一封中文邮件配一份英文 PDF 是最难向用户解释的错位。
因此邮件正文的标题、摘要、金额格式、`<html lang>` 全部跟着 PDF 走。

### 附件能力是如实声明的

`emailSender` 接口上有一项 `SupportsAttachments()`，调用方**先问能力再写正文**：
能带附件的写「收据见附件」，不能的写「点下面的按钮下载」。顺序反过来，
正文已经写着「见附件」了才发现带不了。

| 通道 | 附件 | 说明 |
|---|:--:|---|
| `smtp` | ✅ | MIME 附件，go-mail 直接挂 |
| `zeabur` | ❌ | REST 接口没有公开的附件字段 |

Zeabur 的请求体与 Resend 高度同构，附件**很可能**也用同一套 `attachments` 字段 ——
但「很可能」不足以拿来发凭证：未知字段被服务端忽略的表现是「邮件正常送达、附件不翼而飞」，
用户和运维都收不到任何错误。因此如实声明为不支持，改用签名链接投递。
等 Zeabur 正式文档化该字段，把 `SupportsAttachments` 改成 `true` 并在 `Send` 里带上即可。

同样的取向贯穿这条链路：**通道带不了附件时当场报错，绝不静默把附件丢掉再把信发出去**。

### 签名下载链接

链接形如：

```
https://api.example.com/api/pay/receipts/12/9f2c…/download?expires=1774000000&token=…
```

授权来自两处叠加：128 位随机的凭证标识（猜不到）+ 服务端 HMAC 签名（改不动），
与密码重置链接是同一套模型 —— 拿到链接的人即被视为获授权。因此：

- 签名覆盖 **(应用, 凭证标识, 失效时刻)** 三者。少签任何一项，
  拿到一条合法链接的人就能改出另一条合法链接（换应用、换单号、把有效期改到十年后）。
- 密钥派生自 `SECURITY_MASTER_KEY`（用途盐 `aegis.payment-receipt.link`），
  轮换主密钥会让所有已发出的链接立即失效。
- 有效期默认 7 天（`PAYMENT_RECEIPT_EMAIL_LINK_TTL`），明显长于普通导出的 30 分钟 ——
  邮件可能几天后才被打开，一条半小时就失效的链接等于没发。
- 绝对地址由 `API_BASE_URL` 拼出。未配置时不放链接（邮件里的相对路径点不开），
  若同时又不支持附件，寄送会直接报错而不是发一封空信。

### 收件地址

| 入口 | 收件人 | 理由 |
|---|---|---|
| 用户自助 | **恒为账号绑定的邮箱**，不接受请求指定 | 允许任意填写等于把平台变成一个能带 PDF 附件的转发器：注册一个账号就能以你的域名向任意邮箱发信 |
| 管理端 | 操作者指定 | 客服代发 / 补发到财务邮箱；这条路径走审计中间件 |
| 自动寄送 | 下单用户的绑定邮箱 | 没绑邮箱静默跳过 —— 那不是错误，只是这条链路无处可送 |

用户自助补发有频次上限（`PAYMENT_RECEIPT_EMAIL_PER_DAY`，默认每邮箱每天 10 封）。
统计口径直接取 `email_deliveries` 投递留痕，不另建计数表 ——
多存一份计数只会多一处可能和事实对不上的数字。失败的投递同样计入：
反复触发失败发信一样在消耗上游配额与发信域名的信誉分。

### 支付成功自动寄送

应用级开关，在既有的「交易设置」里（控制台 `/apps`，或 `PUT /api/admin/apps/{appkey}/commerce`）：

```json
{
  "integralPerCurrency": 100,
  "receiptEmailOnPaid": true,
  "receiptLocale": "zh-Hans",
  "walletCurrency": "CNY"
}
```

> 这四项**必须整体提交**：`PUT` 是全量覆盖，只发一个字段会把其余三个静默重置。

`receiptLocale` 留空则按用户设置协商。填了会**当场校验**是不是渲染器认识的语言 ——
存一个不认识的语言，表现是几个月后某封凭证邮件悄悄变成了英文，那时候没人会想到是这里配错了。

只在**首次**确认支付时触发（回调会重复到达，挂在每次回调上会让一次重放多出一封收据），
且全程异步、失败不反噬支付链路：钱已经收到、履约也已完成，
此时因为发信失败让回调返回错误，只会让上游反复重放一笔已完成的支付。

**同一个开关也管余额直购会员**：用钱包付的钱与用支付宝付的钱，
收不收得到收据不该有区别。幂等重放不再寄一次 —— 用户重试一下网络请求不该多收到一封收据。

但**不挂钱包消费与调账**：`consume` 是接入方自定义的业务扣费，一天可能发生几百次，
每次寄一封信会先把邮件出口的配额烧光、再把用户的收件箱埋掉。这两类的凭证按需自取。

## 币种

`payment_orders.currency` 在**下单时**按渠道配置固化（迁移 `000068`）。
不在开凭证时回读 `payment_configs`：商户随时可能把 Stripe 的计价货币从 USD 改成 EUR，
配置改了不该让三个月前已经收过的那笔钱在凭证上变成另一种货币。

取值顺序：渠道配置的 `currency` → 渠道 `Describe()` 自述的 `Currencies` 首项。
走自述而不是在支付服务里另建一张 method → 货币的表 ——
两处各维护一份，早晚会出现凭证上印着渠道根本不支持的货币。
`TestEveryProviderDeclaresCurrency` 钉住「每个渠道都必须自述至少一种货币」。

历史订单（`currency` 为空串）按同样的顺序推断。迁移刻意不给默认值：
直接写死 `'CNY'` 会让一笔真实的美元订单在凭证上变成人民币，那是伪造凭证。

### 钱包的币种

钱包余额没有币种列（余额只是一个数），因此钱包凭证的币种来自**应用级**配置
`walletCurrency`（默认 `CNY`，形状校验为 3 位 ISO 4217 大写字母）。
未配置时退回余额渠道自述的首选货币，与订单那条是同一规则。

它是应用级而不是平台级的：同一个平台上完全可能一个应用收人民币、另一个收美元。
只校验形状不比对币种全表 —— ISO 4217 每年都在增删，维护一张会过期的白名单
只会让某天上线的合法币种被拒；形状校验已经挡住了「人民币」「￥」这类真正会印坏凭证的输入。

## 退款怎么显示

凭证上的「已退款」只统计**退款单里已成功**的部分，
而不是订单上的 `refunded_amount` —— 后者记的是「已占用额度」，包含还在途中的退款，
拿它去印凭证会让用户看到一笔还没到账的退款，直接引发客诉。

尚未提交上游的 `pending` 退款单不出现在凭证上：它还不是一笔已发生的资金往来。

## 落盘与清理

两步式导出的文件落在 `PAYMENT_RECEIPT_ROOT_DIR/<appid>/<billId>.pdf`，
同目录下一份 `.meta.json` 记录归属与过期时间。

- 下载时**同时核对 appid 与 userId**：只把 billId 随机化不足以防越权；
- billId 必须是纯十六进制，挡住 `../` 路径穿越；
- 过期文件由后台清扫协程按 `PAYMENT_RECEIPT_CLEANUP_INTERVAL` 删除；
- 管理端代开**不落盘** —— 那是一次性下载，没有分享场景，落盘只会在磁盘上多留一份交易明细。
