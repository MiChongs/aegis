# 数据库：并发、吞吐与不丢数据

2026-11-08 01:20–02:45，线上 Postgres 每 10 分钟的日志从平时的 4 行涨到 200–1300 行，约 1650 次「查询被取消」。
卡住的几乎都是 `SELECT id FROM users WHERE id = $1 AND appid = $2 FOR UPDATE`，同时有大量 `lottery_draws` 的聚合查询。

查下来是三件事叠在一起：

1. **抽奖事务在持有用户行锁时做 O(N) 聚合**。一个持有 5.6 万次卡密次数的人用旧版 App 连续并发十连抽，
   76 分钟抽了 3.6 万次。每一次抽奖都要扫当天全部记录（积分预算、全站中奖率）和这个人的全部记录（每个奖品中过几次），
   积分预算那一条单次 1 秒，而且记录越多越慢。抽奖的改造见 docs/lottery.md「容量与并发」。
2. **同一个人的并发请求都在库里排队**。每个排队的请求占着一条连接等它自己的用户行锁。
3. **连接池只有 10 条，整站共用**。几个人一起抽，池就被占满，所有功能的请求在池外排队，客户端等不及先断开。

另外，库本身用的是 Postgres 的出厂参数：32 GB 内存的机器上 `shared_buffers` 只有 128 MB，600 MB 的抽奖表放不进缓存。

这次改造的原则：**热路径上没有 O(N) 的查询，没有全站一行的热点，持锁的事务里只有点查与点写，所有计数与留痕都不丢**。

## 连接池

- `POSTGRES_MAX_CONNS` 不配时按每核 4 条，16–40 之间（`config.DefaultPostgresMaxConns`）；`POSTGRES_MIN_CONNS` 默认 4。
  上限 40 是给滚动发布留的：新旧两个实例同时在线是 80 条，库的 `max_connections` 要大于它（见「库侧参数」）。
- 会话级超时在建连时写死（`internal/db/postgres.go`）：语句 30 秒、事务里发呆 60 秒、等锁 10 秒。
  抽奖事务把等锁压到 3 秒（`set_config('lock_timeout', '3s', true)`）。
- **持有一条连接时不能再从同一个池借第二条**：池满时每个持有者都在等第二条，整个池死锁。
  `TestLotteryScaleIntegration` 用只有 4 条连接的池并发抽限量奖品，专门守这一条。

## 行锁纪律

- 用户行锁（`lockUserRowTx`）拿在事务开头、持有到提交。持锁的事务里只允许按主键或唯一键的点查与点写，
  不允许按记录聚合。需要「今天抽了几次」「一共发了多少」这类事实时，维护计数，不要现数。
- 同一个人的请求先在进程内排队（`pkg/keyedgate`：同一时刻一个，最多排 4 个、最多等 5 秒，超出的立刻回「稍后重试」），
  排队的请求不占连接。多实例之间仍靠行锁串行。
- 全站共享的计数不能是一行：拆成分片行（限量库存），或者在事务里追加增量、后台合并（全站计数）。
- 多张表、多行一起更新时按固定顺序加锁（按主键排序），避免死锁。
- 锁等待超时、死锁、串行化冲突、语句超时不是程序错误：HTTP 层统一回 503 + `Retry-After: 1`，业务码 50310
  （`transport/http/dto.go` 的 `databaseBusy`）；抽奖回 40925「抽奖正在处理，请稍后重试」。

## 风控留痕

每一次风控评估都要留痕：一条评估记录，加上规则命中数、名单命中数、IP 计数、设备指纹。以前每次评估起一个 goroutine
逐条写：评估量一大，这些 goroutine 不受限地抢连接池；「规则命中数 +1」是全站一条规则一行，所有人都在改同一行。

现在经 **NATS JetStream**（nats.go v1.55 的 `jetstream` 包）可靠地异步写库（`service/risk_trail.go`）：

- **流** `AEGIS_RISK_TRAIL`（主题 `risk.trail`）：工作队列（确认即删）、文件存储、S2 压缩、两分钟去重窗口、上限 2 GB，
  满了拒绝新消息（`DiscardNew`，不丢旧的）。
- **发布**：评估完同步发布、拿到服务端确认才返回（本机 1000 条并发发布共 73 ms），带事件 ID（UUIDv7，`Nats-Msg-Id`）。
  发布拿不到确认（NATS 不可用、流满、流还没建好）时**退回直接写库**；直接写库也失败时，整条留痕进错误日志，能从日志补回。
- **消费**：每个 API 实例 2 个持久拉取消费者（同一个 durable `risk-trail-writer`，一条消息只给一个实例），一次取 500 条或等
  500 ms，在**一个 Postgres 事务**里写完（`Repository.WriteRiskTrail`）：
  1. 事件 ID 插进 `risk_trail_events`，插得进去的才是第一次见到的；
  2. 只对这些用 COPY 写评估记录；
  3. 规则命中数、名单命中数按 ID 合并成一条 UPDATE，IP 计数、设备指纹按键合并成一条 UPSERT（都按键排序）。
  提交之后才逐条确认。
- **不丢、不重**：写库失败 → 整批延迟 5 秒重投；进程在提交前崩溃 → 没确认的消息过了 AckWait（1 分钟）重投；
  提交后、确认前崩溃 → 重投的那批在去重表里全部撞上，什么都不做。重投次数不限（`MaxDeliver -1`），
  只有解不开的消息（代码错误）会被终止并记错误日志。实例下线时没取走的消息留在流里，下一个实例接着写。
- 去重记录保留 8 天，每小时清理一次。封禁这一路仍然同步写（要拿评估 ID 记处置）。
- `TestRiskTrailIntegration`（内嵌 nats-server）：1000 条并发留痕全部落库且各项计数恰好加 1000；写库协程停掉期间发布的
  200 条留在流里，换一个实例启动后写完、流清空；同一条重复发布、重复写库只算一次；NATS 挂掉时退回直接写库，一条不少。

为什么不用别的：River（Postgres 任务队列）适合「与业务同一事务入队」的任务，但每条留痕要多写一行任务表，写库量翻倍；
Redis Stream 或 Lua 脚本要求 Redis 可靠落盘，线上 Redis 的启动参数里没有开 AOF，宕机会丢最近的数据。

## 库侧参数

`deploy/docker/postgres/tuning.sql`（`ALTER SYSTEM`，写进数据目录，容器重建后仍生效），按 8 核 / 32 GB、与其它服务同机估算：
`shared_buffers` 4 GB、`effective_cache_size` 16 GB、`work_mem` 16 MB、`max_connections` 200、`max_wal_size` 4 GB、
`random_page_cost` 1.1、自动清理更积极、`pg_stat_statements` 与慢语句 / 等锁日志。标「重启」的参数要重启 Postgres
才生效（几秒中断）。容器的 `/dev/shm` 默认只有 64 MB：`min_dynamic_shared_memory` 256 MB 让并行查询先用主共享内存里预留的
一块，不受它限制（线上的基础设施 compose 存在 Dokploy 里，改 `shm_size` 要整套重新部署，所以用这个参数代替）。

JetStream 默认每 2 分钟把文件存储刷一次盘（`sync_interval`），进程崩溃不丢、整机断电可能丢最近的未刷盘部分；
要连断电都不丢，nats-server 配 `jetstream { sync_interval: always }`（写入变慢）。

## 容量

单机（本机 Docker Postgres 17、连接池 40 条）的抽奖压测：单抽约 2300–3400 次/秒、十连抽约 3300–5300 次/秒，
比改造前快 1.5–1.9 倍（`TestLotteryLoad`，与改造前的代码在同一时段交替跑，见 docs/lottery.md）。
抽奖事务里互不依赖的读都走 pgx 的批量管道（`repository/postgres/pgpipe.go`），单抽 7 次往返。
「200 万人」指的是用户规模：抽奖、风控留痕的每一步开销都与用户数和历史记录数无关（计数 O(1)、分片无热点），
吞吐只随库的 CPU 与连接数涨。再往上的手段按顺序：调库侧参数 → 加 API 实例（多实例之间已经安全：咨询锁、行锁、
工作队列消费者都按多实例设计）→ PgBouncer 事务池化 → 读写分离 → 按时间分区 `lottery_draws` 与 `risk_assessments`。
